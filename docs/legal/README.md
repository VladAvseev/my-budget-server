# Исходники юридических документов

Каталог markdown-текстов, из которых CLI `npm run legal:publish` публикует БД
(реализация `PersonalData.md`, п.2: файл в git — исходник/вход CLI, канон
опубликованных версий — таблица `legal_documents`).

## Два документа

| Файл                | `document_type`  | Slug в клиенте          | Гейтит? |
| ------------------- | ---------------- | ----------------------- | ------- |
| `privacy_policy.md` | `privacy_policy` | `/legal/privacy-policy` | да — блокирующий consent-gate, отзыв = обезличивание |
| `terms_of_use.md`   | `terms_of_use`   | `/legal/terms-of-use`   | нет — только ссылка       |

- **`privacy_policy.md`** — политика конфиденциальности. Единственный тип,
  участвующий в consent-gate: её принятие при регистрации и в gate'е
  юридически считается согласием на обработку персональных данных; публикация
  новой версии переводит всех пользователей в `NEEDS_CONSENT` при следующем
  входе. Отдельного документа «Согласие на обработку ПДн» на сайте нет.
- **`terms_of_use.md`** — пользовательское соглашение: информационный
  документ, его новые версии НЕ инвалидируют согласия (CLI пишет об этом
  прямо в ответе публикации).

Оба реестра обязаны совпадать: `KNOWN_DOCUMENT_TYPES` в
`src/modules/_legal/types.ts` (сервер) ↔ `src/shared/legal/documents.ts`
(клиент). Новый тип = правка обоих + этот каталог.

## Правила подготовки файлов

1. **Только тело документа**: без «Примечаний для оператора», «Чек-листов» и
   хвостовых комментариев модели — это не публикуется, но остаётся в тексте.
2. UTF-8 без BOM, LF (`.gitattributes` нормализует), чистый Markdown/GFM.
   Клиент рендерит react-markdown без raw HTML: `<br>`/`<div>` превратятся в
   текст — CLI отклоняет опасные теги и предупреждает об остальных.
3. Заполнить все `[ПЛЕЙСХОЛДЕРЫ]` (CLI предупреждает о квадратных скобках):
   статус оператора (ИП/физлицо в РБ), ФИО, адрес, **email для обращений
   субъектов ПДн**.
4. В тексте гейтящей политики должны присутствовать слова «согласие/соглашаюсь»
   и email оператора — CLI проверяет это префлайтом (`--strict` блокирует
   публикацию при любых предупреждениях).
5. Публикация с незаполненными плейсхолдерами — юридически дефектная «действующая
   редакция»: при сомнениях гоняй `--dry-run`/`--strict` до записи в БД.

## Публикация

```bash
# dev (из server/): файл по умолчанию = docs/legal/<type>.md
npm run legal:publish -- --all --dry-run     # префлайт + дифф с БД, ничего не пишет
npm run legal:publish -- --all               # опубликовать все имеющиеся файлы
npm run legal:publish -- --type privacy_policy  # один документ
npm run legal:verify                         # целостность всех типов из БД
npm run legal:verify -- --type privacy_policy   # один тип
```

```bash
# прод (из /opt/mybudget/server; docs/legal смонтирован в api как /docs)
docker compose exec api node dist/scripts/publish-legal-document.js --all --docs-dir /docs --dry-run
docker compose exec api node dist/scripts/publish-legal-document.js --all --docs-dir /docs
docker compose exec api node dist/scripts/publish-legal-document.js --verify
```

merge в `develop` ≠ опубликовано: пока не вызван CLI, пользователям отдаётся
прежняя current-версия из БД. Повторная публикация идентичного текста
отклоняется (защита от холостой инвалидации согласий). Версия = дата по МСК,
конфликт дня → суффикс `-2`. Косметическая правка (орфография без смены версии
и инвалидации) — флаг `--cosmetic`, факт фиксируется в коммите.

**Порядок первого включения в проде** (гейтящий документ ещё не публиковался):

1. deploy-api (код уже поддерживает оба типа);
2. `--dry-run` — проверить тексты;
3. `--type terms_of_use` (информационный — согласий не касается);
4. `--type privacy_policy` — с этой минуты гейт активен у всех, регистрация
   работает как задумано;
5. deploy-web (ссылки в футере/регистрации/профиле/Gate) — после публикации,
   иначе ссылки ведут на «Документ не найден»;
6. `--verify` — зафиксировать состояние.
